## 🔐 Auditoria do sistema (12/07) — verificada e corrigida
A auditoria (dashboard, commit a2f1d9f) apontou **33 achados altos / 0 críticos**. É **estática
(só código)** e não enxerga RLS/triggers — então cada achado foi verificado contra o código e o
banco reais. Resultado:

**✅ CORRIGIDO — crítico real (escalonamento de benefícios):** a RLS de `perfis` permite o usuário
atualizar o **próprio** perfil, e o trigger `proteger_campos_sensiveis_perfil` só revertia
role/ativo/indicado/bonus_mercado. Ficavam **graváveis pelo cliente**: `plano`, `plano_vencimento`,
`bonus_documental`, `analises_bonus`, `comissao_afiliado_pct`, `comissionamento_bloqueado`,
`comissionado_por` → um usuário comum podia se **auto-conceder plano pago, análises grátis e
comissão**. **Fix:** trigger estendido a esses campos (migração `20260712_proteger_campos_sensiveis_perfil_financeiro.sql`,
aplicada). Endpoints server-side usam service_role → não afetados. Admin também não é afetado (bypass no trigger).

**✅ CORRIGIDO — crítico real (acesso a dados de OUTROS usuários / RPC pública):** as funções
SECURITY DEFINER `admin_busca_usuarios(termo)` e `admin_usuario_360(uid)` estavam **chamáveis por
qualquer um** (inclusive anônimo) via `/rest/v1/rpc/...`. As migrações anteriores tentaram travar com
`revoke execute ... from anon, authenticated`, mas isso é **inefetivo no Postgres**: o EXECUTE é herdado
de **PUBLIC** (grant default na criação da função) e não se revoga um grant de PUBLIC revogando de um
papel específico — a ACL seguia com `=X` (PUBLIC). Na prática, qualquer pessoa podia POST
`{uid}` em `admin_usuario_360` e receber **perfil + e-mail + último acesso + atividade de outro usuário**,
ou listar nome/e-mail/plano em `admin_busca_usuarios` — contornando o endpoint admin-gated
`api/admin-usuario-360.js`. **Fix:** `REVOKE EXECUTE ... FROM PUBLIC` (migração
`20260712_revoke_public_execute_funcoes_admin_definer.sql`, aplicada) — ACL agora
`{postgres,service_role}`. O painel admin continua funcionando (o endpoint chama via service key). Mesmo
fix aplicado às internas `demanda_busca_agregada()` e `auditoria_funcionamento()` (fluxo do sistema,
só server-side).

### 🛡️ Os 3 pilares de segurança do dono — verificados e fechados (12/07)
1. **Usuário NÃO altera o próprio nível (plano/role) sem pagar.** RLS deixa o usuário atualizar o
   próprio perfil, mas o trigger `trg_proteger_perfil` (habilitado, verificado no banco) reverte
   `role`, `plano`, `plano_ciclo/pago_em/vencimento`, `bonus_documental`, `analises_bonus` e os campos de
   comissão para `authenticated`/`anon` não-admin. Confirmado por query: **nenhuma** função SECURITY
   DEFINER escreve `perfis.plano`/`role` por um caminho alcançável pelo usuário. Pagamento concede plano
   via service_role (bypass legítimo do trigger). ✔
2. **Usuário NÃO acessa dados de outros usuários.** RPCs `admin_busca_usuarios`/`admin_usuario_360`
   travadas (acima). `perfis` SELECT restrito a próprio + carteira do consultor + equipe + admin. Demais
   RPCs SECURITY DEFINER executáveis por usuário são *self-guarded* (operam só sobre `auth.uid()`:
   `is_admin`/`is_equipe`/`app_role`, `registrar_imovel_visto`, `gerar_codigo_indicacao`) — nenhuma
   retorna dado de terceiro. ✔
3. **Usuário NÃO entra no fluxo interno sem permissão (convite ou habilitação manual do admin).**
   `usar_convite`/`usar_convite_equipe`/`vincular_indicacao`/`gerar_codigo_indicacao` validam
   `auth.uid()` e o token do convite (válido/não-usado/não-expirado). Habilitação manual = admin muda
   role/plano (bypass do trigger via `is_admin()`). Funções internas de sistema
   (`demanda_busca_agregada`/`auditoria_funcionamento`) travadas para só server-side. ✔

**✅ CORRIGIDO — gate fail-open:** `gerar-laudo-viabilidade.js` liberava o laudo pago se a checagem
de plano lançasse erro (catch vazio) → agora **falha fechado** (503 retornável).

**❌ FALSO-POSITIVO (verificado):** `verificar-cpf` **não** expõe userId/role (só `{temConta,temAcesso}`
booleans + rate-limit); **IDOR de `casos`** — RLS restringe SELECT ao dono (cliente/analista/advogado/admin)
e não há INSERT p/ cliente; **role/atribuir/toggleAtivo (Admin.jsx)** — trigger reverte p/ não-admin;
**KYC via RPC `salvar_kyc_equipe`** — SECURITY DEFINER + RLS.

**⏳ FOLLOW-UP (registrar, corrigir depois — não exploráveis triviais / hardening):**
- `identidade_validada` setado no cliente (Perfil.jsx) → mover para `/api/validar-selfie` (service key) e
  então protegê-lo no trigger (hoje ficou de fora p/ não quebrar o KYC). Baixo impacto (não gateia ação sensível).
- **SSRF** (`geocodificar-imovel`, `gerar-documental`, `processar-analise`): reusar `hostPermitido()` do
  `fetch-url.js` para validar destino de URLs de documento vindas do banco/cliente.
- **Token de unsubscribe fraco** (`email-alerta`/`cancelar-alertas`): trocar `btoa()` por HMAC e remover
  fallback hardcoded `'bidpro'` (fail-closed). Impacto: só alertas de e-mail.
- **`upload-anexo`**: qualquer autenticado sobrescreve anexo não-staff → checar ownership do imóvel.
- **PIX estático** (`PagamentoServico`/`mp-verificar-pix`): trocar por txid/referência única por cobrança.
- **`push-send`**: cifra Web Push incompleta (VAPID `raw`→`pkcs8`) — push provavelmente não funciona; sem risco de dado.
- **Checagem de role só no front** (AdminChargebacks/AdminFinanceiro/Atendimento): as APIs validam server-side
  (defesa em profundidade); confirmar caso a caso.
